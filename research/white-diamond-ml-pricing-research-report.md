# White-Diamond ML Pricing — Consolidated Research Report

**Status:** Living research report (single entry point)  
**Date:** 2026-05-31  
**Audience:** Founders, engineers, and anyone asking “what’s wrong, what are we building toward, and what might be better?”

This document merges the substance of the scattered `research/*.md` notes, the **canonical training dataset**, benchmark numbers, chart findings, and design constraints into one narrative. Use it to decide whether a new model family can beat what ships today.

**Report map:** §2 = cleaned dataset (what it is, what we optimize toward) · §3 = model iterations tried (S7–S28) · §4–§9 = constraints, inventory, evidence, candidates · §14 = conclusion.

## Executive summary

**The problem:** StarGem wholesale lab-grown diamond prices are not generated by one smooth function of carat and grade. The same nominal spec (shape, color, clarity, carat band) often contains **multiple price modes** (old rate card vs current list, commodity vs premium cut, specialty faceting vs standard). Any model must either **interpolate** the sheet accurately or **extrapolate** to unseen specs with defensible gem-market structure — usually not both in a single unconstrained estimator.

**What ships today (white):** **S26** — a champion **policy** that blends StarGem **lookup reconstruction**, monotone-capped **S22/S23** trees, and (in the app) live **comps**. It achieves ~**4.8% MAPE** on dense Segment-A rows because lookup *is* the sheet in covered cells. It is **piecewise constant in carat** (bucket steps), which is correct for audit but wrong as the long-term pricing *law*.

**What we are prototyping:** **S28** — one **monotone parametric** log($/ct) surface over `dataset-clean-training.json`. It is the only stack member **designed** for continuous extrapolation with hard sign constraints. **v0.2 holdout MAPE ~8.8%**, but charts and cell checks show it is often **20–35% below** dense commodity cells (e.g. ROUND E VS1) and can **fall in $/ct between 1ct and 5ct** for common grades — a monotonicity gap not caught by training gates that only test ROUND D IF.

**Recommended direction (“something better”):** Do not replace S26 with pure S28. Build:

```text
cell anchor (lookup or spec offset)
  + continuous monotone surface in carat (S28+, fixed grade×size monotonicity)
  + shrunk monotone residual ML where support exists
  + isotonic ladder projection for display guarantees
```

**Colored gems:** Separate family — **S27 / Color S22** champion; do not route white S28 into fancy-color stones.

**Clean dataset (§2):** `dataset-clean-training.json` — **21,982** Segment-A rows from style-aware cluster quarantine (**559** highs/outliers removed). Target = **competitive current-list** wholesale ($/ct), not every historical mode; ~**3%** within-spec noise floor. Still **multiple prices per cell** when commodity and premium share a cluster.

**What we tried (§3):** Trees (S7/S18) → lookup residual **S19** → specialty **S20** → monotone **S21/S23** → benchmark blend **S22** → champion **S26** (~4.8% MAPE) → parametric **S25** (broken tail) → surface **S28** (structure yes, level no). Next bet: **anchor + S28 + shrunk residual** (§8.1).

## 1. Problem statement

### 1.1 What we need the system to do

| Task | User question | Success looks like |
|------|----------------|-------------------|
| **Interpolation** | “What does StarGem charge for this exact bucket today?” | Within a few % of the competitive list / lookup cell |
| **Extrapolation** | “What should a 7.77ct ROUND E VS1 cost if we have few 7.77ct rows?” | Monotone, plausible $/ct; no clarity/color inversions; tail scarcity not collapsed to commodity |
| **Explanation** | “Why is this number different from comps / ML?” | Source blend, support tier, out-of-range flags |
| **Trust** | “Is better clarity cheaper?” | Never on ladders or constrained surfaces |

### 1.2 Core tension

```text
Low MAPE on the historical sheet  ⟺  memorize buckets, eras, and bimodal tails
Safe extrapolation             ⟺  smooth law + constraints + fewer degrees of freedom
```

One unconstrained model optimizing only MAPE will:

- fit **premium and commodity** rows in the same cell;
- **step** at internal `carat_bucket` boundaries;
- **invert** clarity or color in sparse tree leaves (documented for S22);
- **collapse** large-carat tails (S25 negative global carat β).

The codebase already **split roles**: S26 for dense policy, S28 for structural surface. This report argues that **neither alone is the end state**, and documents evidence for the next hybrid.

### 1.3 Why charts look “not log-shaped” and “not smooth”

Observed causes (not plotting bugs):

1. **Scatter:** Raw `starsgem-index` mixes rate-card eras (~2× spread for “same” spec). Clean training removes unexplained **high clusters** but still leaves many rows per cell.
2. **Lookup / S26:** Price is constant inside `carat_bucket`, then jumps at `2.99 → 3.01` when the bucket label changes — **not** because the market jumps there alone.
3. **S28 v0.2:** Global ridge surface **under-levels** popular cells; `colorRank_size` / `clarityRank_size` terms can **reduce $/ct as carat grows** for E/VS1-style specs while tests only validate D/IF.
4. **Lab-grown commodity segment:** **$/ct** is often **higher at 1ct than 3ct** on the sheet (listing economics), so the cloud slopes down in $/ct even when **total price** rises with carat.

### 2.2 How the clean dataset is built

**Input:** `starsgem-index.json` (IGI-enriched; ~22,541 white rows).

**Style buckets** (examples — do not merge distinct IGI styles):

```text
ROUND_STANDARD, PEAR_STANDARD, PEAR_MODIFIED, PEAR_ICE_FLOWER,
OVAL_STANDARD, OVAL_MODIFIED, RADIANT_MODIFIED, HEART_STANDARD, …
```

**Cluster key (style-aware):**

```text
round(carat, 2) + shape_style + color + clarity
```

**Rules:**

1. Sort by $/ct within each group.
2. If largest consecutive jump ≥ **30%** and both sides are meaningful clusters (low ≥ 2, high ≥ 2, low count ≥ high count) → **quarantine high cluster** as `H_high_price_cluster`.
3. Else if lone point ≥ **40%** above group median → `F_extreme_outlier`.
4. Else → **`A_standard_recent`** (training).

**Intent:** Keep the **competitive / base** price surface; drop unexplained high tails (stale rate cards, unlabeled premiums). **Not** “lowest price only,” but “lower explained cluster when bimodal.”

See also: [`master-dataset-removal-audit.md`](master-dataset-removal-audit.md), [`same-spec-price-spread-examples.md`](same-spec-price-spread-examples.md).

**Builder:** `python3 research/scripts/dataset-split-outliers.py` → `npm run research:build-master-dataset`

### 2.3 What we are trying to get close to (target estimand)

ML is not trained to predict “any price StarGem ever listed.” The cleaned dataset defines a deliberate **target**:

| Layer | Definition | Use |
|-------|------------|-----|
| **Raw index** | All priced IGI-enriched rows in `starsgem-index.json` | Diagnostics, gray dots on charts, comp index |
| **Clean training (`A_standard_recent`)** | Rows that pass style-aware cluster rules | **Canonical ML target** |
| **Competitive list / lookup cell** | Median (or reconstructed rate) in `carat_bucket × shape × color × clarity [× cut]` on **current-window** stock | What **S26** chases (~4.8% MAPE) |
| **Continuous wholesale law** | Monotone $/ct in carat + grades, magic weights only, valid on **empty** cells | What **S28+** should encode after cell anchor |
| **User-facing hero (R0)** | Reconciled wholesale from comps + ML + baseline rules | App headline; ML is one input ([`r0-decision-log.md`](r0-decision-log.md)) |

**In plain language, we want models to get close to:**

1. **“What does this supplier charge *right now* for stones like this?”**  
   → Best answered by **lookup + S26-class policy** on dense SKUs (e.g. 3ct ROUND E VS1 ≈ **$109/ct** commodity median, not the $169/ct premium tail).

2. **“What is a defensible wholesale $/ct for a spec we rarely stock?”**  
   → Needs **structure** (monotone carat/grade) + **sparse data**, not bucket stairs alone.

3. **“Never show impossible gem logic.”**  
   → Better clarity/color must not price below worse; display ladders may use **PAV** on top of point models.

**What we explicitly do *not* treat as ground truth:**

- Old rate-card rows left in the raw index (gray scatter above rose cloud).
- Unexplained **high-price clusters** quarantined as `H_high_price_cluster` (stale list / duplicate era).
- Premium ID/EX tails in the same cell as commodity CVD when the cluster rule keeps the **lower** mode.
- Alibaba comp medians as the ML label (comps inform R0 and high-carat S26; they are not the training JSON).

**Noise floor (within-spec spread, clean training):**  
On Segment A, median absolute deviation from per-group median is ~**2.77% MAPE-equivalent** across 2,244 style/spec groups ([`dataset-split-summary.json`](data/dataset-split-summary.json) `noise_floors.seg_a`). So even a **perfect** model cannot expect much below ~3% global MAPE without changing the label (e.g. time-stamping “price as of today”).

### 2.5 Row schema (what each training example contains)

Each object in `dataset-clean-training.json` is one priced stone. Typical fields:

| Field | Role |
|-------|------|
| `rowNo` | Supplier sheet row (used for vintage / rate-card era features in S28) |
| `reportno` | IGI report id |
| `carat`, `price`, `upc` | Size and **StarGem list price** (training label = `upc` or `price/carat`) |
| `shape`, `raw_shape_code` | Supplier shape code |
| `shape_style` | **ML bucket** — e.g. `ROUND_STANDARD`, `PEAR_MODIFIED`, `OVAL_ICE_FLOWER` |
| `color`, `clarity` | White grades (D–J, IF–SI2) |
| `cut_raw`, `polish`, `symmetry` | Cut/polish/symmetry codes |
| `typeName` | CVD / HPHT |
| `lw_ratio`, `table_pct`, `depth_pct` | IGI dimensions (when enriched) |
| `igi_shape_raw`, `igi_shape_mapped` | Cert text → normalized shape |
| `segment`, `segment_reason` | Always `A_standard_recent` in training file; reason text for audit |

**Example (abridged from training JSON):**

```json
{
  "rowNo": 2,
  "carat": 40.11,
  "upc": 1219.5,

```

**Important:** Training is on **physical style** (`shape_style`), not supplier shape label alone. `Pear Brilliant` vs `Pear Modified Brilliant` stay separate when IGI confirms them.

### 2.6 What was removed vs what remains inside a “clean” cell

| Situation | Action |
|-----------|--------|
| Two price modes, same `round(carat,2)+shape_style+color+clarity`, no feature explains high tail | Drop **high** cluster; keep **base** cluster |
| One stone far above median | Quarantine as `F_extreme_outlier` |
| Specialty cut with own IGI style (`PEAR_ICE_FLOWER`, etc.) | **Keep** in its bucket; do not merge into standard pear |
| Old row number but stone is valid large modern inventory | **Keep** (e.g. 13ct+ rounds after IGI enrichment fix) |
| Commodity + premium ID/EX still in **same** cluster after rule | **Both can remain** if not separated by 30% cluster split — model still sees spread |

So “cleaned” ≠ “one price per spec.” It means **removed unexplained stale highs**, not removed all variance.

### 2.7 What the dataset can and cannot teach

| Can learn | Cannot reliably learn without more data |
|-----------|----------------------------------------|
| Dense 1–3ct round commodity (E/VS1, etc.) | 4ct+ specialty hearts with few rows per style |
| Shape/style modifiers when `shape_style` has support | One global surface without per-cell anchor |
| Large stones **where style bucket has rows** | Exact 30ct IF premium if cell empty |
| Lower-cluster wholesale floor | Full bimodal premium distribution |
| Within-spec spread ~3% “noise floor” | Sub-2% MAPE on all segments |

Large-carat outputs must report **`shape_style` support**, not only global max carat ([`ml-training-data-policy.md`](ml-training-data-policy.md)).

### 2.8 Known data pathology (still present in clean data)

**Temporal / rate-card mixing** — Same spec, 2× spread; expensive rows often early `rowNo`, `传统切` on old cards ([`same-spec-price-spread-examples.md`](same-spec-price-spread-examples.md)).

**Commodity vs premium in one bucket** — e.g. 241× `3ct ROUND E VS1`: ~$109/ct commodity vs ~$169/ct premium ID/EX ([`starsgem-ml-training-diagnosis-and-retrain-plan.md`](starsgem-ml-training-diagnosis-and-retrain-plan.md)).

**Specialty cut styles** — `传统切`, `冰花切`, etc. at 2–6× standard in same nominal shape/color/clarity ([`starsgem-ml-training-diagnosis-and-retrain-plan.md`](starsgem-ml-training-diagnosis-and-retrain-plan.md)).

**Outliers** — e.g. $19/ct at 5ct+ likely data error; audit before training.

## 3. Model iteration history — what we have tried

Chronological summary of white-diamond ML approaches in this repo. Earlier generations live in `research/scripts/starsgem-mrpe-v2.py` (S7–S18); production iterated through S19–S28.

### 3.1 Approach families

| Family | Idea | Strength | Failure mode |
|--------|------|----------|--------------|
| **Pure trees** (S7, S18, S20, S22) | ExtraTrees on features + lookup anchor | Low MAPE in dense cells (~4–6%) | Global fallback; clarity inversions; OOD carat flat/wrong |
| **Lookup residual** (S19–S20) | Predict `log(actual/lookup)` | Fixes “relearn the sheet” | Still bucket-anchored; selected-spec drift |
| **Monotone boosting** (S21, S23) | LightGBM + monotone constraints | Grade ladders safe | Fights sparse anchor; worse MAPE than S20 alone |
| **Parametric** (S25, S28) | log($/ct) surface | Always prices; extrapolation | S25 negative carat β; S28 low level + grade×size bug |
| **Champion policy** (S26) | Blend lookup + ML + comps | Best **interpolation** today | Piecewise in carat; not one smooth law |
| **Post-process PAV** (S22 display) | Isotonic on ladder | Guarantees display | Worsens point MAPE if used for pricing |

### 3.4 What we have *not* yet tried (candidates from reports)

- **S28 + specAnchor** (`lookup` or shrunk `specEps`) — top recommendation in [`ml-extrapolation-vs-in-sample-accuracy.md`](ml-extrapolation-vs-in-sample-accuracy.md).
- **Monotone residual on `log(actual / S28)`** with LightGBM — belt-and-suspenders per [`monotonic-models-and-generalized-grade-modifier.md`](monotonic-models-and-generalized-grade-modifier.md).

- **Two-mode mixture** (commodity vs premium) within cell — data has bimodal spread; only cluster split attempted so far.
- **Train only last-N-days** pricing — needs reliable “listed at” timestamp ([`mape-floor-root-cause-analysis.md`](mape-floor-root-cause-analysis.md)).

## 4. Constraints (hard requirements)

These are **product and market rules**, not optional regularization.

### 4.1 Ordered attributes (white diamond)

| Attribute | Order (better → worse for price) | Direction of $/ct |
|-----------|----------------------------------|-------------------|
| Clarity | IF > VVS1 > VVS2 > VS1 > VS2 > SI1 > SI2 | Better clarity → **higher** |
| Color | D > E > F > … > J | Better color → **higher** |
| Carat (fixed spec) | larger | Larger → **higher** $/ct (scarcity); total $ increases |
| HPHT vs CVD | same spec | HPHT ≥ CVD |

Registry pattern: [`monotonic-models-and-generalized-grade-modifier.md`](monotonic-models-and-generalized-grade-modifier.md) (`monotone-axes.json` — proposed single source of truth).

### 4.2 Continuous surface (design target)

Full spec: [`continuous-pricing-surface-principles.md`](continuous-pricing-surface-principles.md)

**Policy in one sentence:** Buckets **count** stones; **carat as a float** prices stones. The curve is continuous and upward in $/ct except at **magic weights** (1, 1.5, 2, 3, 4, 5, 10, 20 ct) using ramp + step features — **not** at spreadsheet `carat_bucket` walls.

### 4.3 Allowed vs forbidden discontinuities

| Allowed | Forbidden |
|---------|-----------|
| Ramp/step near 4.0ct, 3.0ct, … | Step only because bucket went `2.99–2.99` → `3.00–3.99` |
| Different **slopes** in log-carat segments | Flat $/ct across 2.8–3.2ct then cliff at bucket label |
| Cell-level **anchor** added to smooth surface | Blending commodity + premium into one “average” without mode handling |

### 4.4 S28 v0.2 acceptance gates (training script)

From [`s28-monotone-parametric-trend-surface.md`](s28-monotone-parametric-trend-surface.md):

1. Zero clarity inversions on fixed grid (ROUND D).
2. Zero white-color inversions on fixed grid.
3. Zero HPHT &lt; CVD inversions.
4. Zero carat $/ct inversions on fixed grid (ROUND D IF).
5. Segment MAPE by carat band and shape.
6. Pinned large-stone cases above S25 floor.
7. Metadata proves training from `dataset-clean-training.json`.

**Gap found in practice:** Gates use **ROUND D IF**; common specs (ROUND E VS1) can violate carat monotonicity in $/ct because `colorRank_size` / `clarityRank_size` push down as carat grows. **Extend gates to a grade grid before any champion swap.**

## 7. Why one model cannot “just learn everything”

See full argument: [`ml-extrapolation-vs-in-sample-accuracy.md`](ml-extrapolation-vs-in-sample-accuracy.md)

**Summary:**

- **S26 low MAPE** = reconstructing the lookup grid (interpolation).
- **S28 discipline** = constrained law (extrapolation); higher MAPE, wrong level without anchors.
- **Trees** = local patches; **lookup** = stairs; **pure parametric** = wrong tail without monotone carat enforcement.

Training on **clean** data helps but does not remove multi-modal noise inside a cell; it removes unexplained **high** clusters.

## 8. Candidate architectures (“something better”)

Ranked by fit to problem + constraints. Each should be judged on the **evaluation protocol** (§9), not headline MAPE alone.

### 8.1 Recommended: Anchor + continuous surface + residual

```text
log($/ct) = specAnchor[shape_style, color, clarity]   // lookup median or shrunk cell offset
          + f_monotone(carat, magic_weights, cut, …)   // S28+, fixed grade×size rules
          + g_residual(x)                                // monotone LightGBM, shrunk to 0 OOD
```

| Piece | Purpose |
|-------|---------|
| **specAnchor** | Fixes S28 under-leveling on ROUND E VS1 |
| **f_monotone** | Continuous carat law; magic weights only |
| **g_residual** | Absorb commodity vs premium **within** cell when support exists |

**Why better than S26 alone:** Smooth in carat for pricing sliders and unseen sizes; anchor keeps dense-cell accuracy.

**Why better than S28 alone:** Correct level per cell; residuals don’t need to invent spec from global pool.

### 8.2 Interpolated lookup + monotone tail

Keep lookup values at bucket **centroids**, linearly or log-linearly **interpolate in carat** between centroids; add monotone tail above 5ct from S20/S28 tail features.

**Pros:** Stays data-anchored. **Cons:** Still tied to bucket support; interpolation can misbehave between sparse buckets.

### 8.3 S25-style specEps + fixed S28 carat law

Revive S25 `specEps[shape||color||clarity]` for level, use S28 only for carat/scarcity shape with enforced nondecreasing $/ct per spec.

**Pros:** Interpretable. **Cons:** Sparse cells still need gradient fallback; specEps doesn’t fix era mixing inside cell.

### 8.4 Two-mode mixture (commodity vs premium)

Explicit latent mode or cut-style split; train separate surfaces or mixture weights.

**Pros:** Models real bimodal sheet. **Cons:** More data and UI complexity; needs cut/style features ([`starsgem-ml-training-diagnosis-and-retrain-plan.md`](starsgem-ml-training-diagnosis-and-retrain-plan.md) P1 specialty cut).

### 8.5 Stay on S26; document as policy not law

**Pros:** Best current MAPE. **Cons:** Does not meet continuous-surface product goal ([`continuous-pricing-surface-principles.md`](continuous-pricing-surface-principles.md)).

## 9. Evaluation protocol (required before “X is better”)

### 9.1 Splits

| Split | Purpose |
|-------|---------|
| **reportHash % 5 holdout** | Row-level (current S28); easy but lookup-leaky |
| **Held-out cells** | Hold out entire `(shape_style, color, clarity, carat_band)` groups |
| **Pinned cases** | Regression smoke tests |

**Do not** claim victory on global MAPE alone.

### 9.2 Metrics (report all)

```text
Global MAPE / MdAPE / bias
MAPE by carat bucket, shape_style, support tier
Pinned case absolute error
Carat grid monotonicity violations (per spec, not only D IF)
Clarity/color ladder inversions
Max |$/ct(c) - $/ct(c+ε)| outside magic-weight windows
```

### 9.3 Pinned white-diamond cases

| # | Spec | Check |
|---|------|--------|
| P1 | 3.00ct ROUND E VS1 ID selected-spec | Near clean median ~$109/ct, not EX tail |
| P2 | 7.77ct ROUND E VS1 | Not below $180/ct floor; comps/lookup alignment |
| P3 | 5.21ct HEART D VS1 | Specialty scarcity, not commodity |
| P4 | 40ct ROUND E VS2 vs SI1 | SI1 display ≤ VS2 |
| P5 | 2.99 vs 3.01ct ROUND E VS1 | Continuous except allowed magic band |

### 9.4 “Better” decision rule

Candidate **B** is better than production **S26** only if:

1. **Dense cells:** MAPE ≤ S26 + 1pp on held-out **cell** split, **and**
2. **Monotonicity:** zero violations on grade grids for all common specs, **and**
3. **Continuity:** $| \Delta \log upc / \Delta carat |$ bounded except at documented magic weights, **and**
4. **Pinned cases:** all pass, **and**
5. **Extrapolation tier:** beats S28 on specs with no lookup cell (heart 8ct+, etc.)

Candidate beats **S28 v0.2** if level matches lookup median within ~5% on top 20 volume cells **and** carat monotonicity holds for E/VS1 and D/IF.

## 10. S28 v0.2 fixes required before it anchors a hybrid

1. **Per-spec carat monotonicity tests** — E VS1, F VS2, not only D IF.
2. **Reparameterize grade×size** — e.g. constrain so fixed grade → nondecreasing $/ct in carat; or use better-grade-is-higher interaction with positive sign only on premium terms.
3. **specAnchor layer** — lookup cell log-offset or shrunk `specEps`.
4. **Optional:** train vintage at `vintage01=1` only for “current list” target if era drift remains in clean set.

## 11. Data policy implications for “smooth training target”

| Approach | Effect on charts | Effect on ML |
|----------|------------------|----------------|
| Raw index scatter | Jagged, bimodal | Don't train |
| Clean training only | Tighter cloud | **Canonical** |
| Lower cluster only (current) | Removes high tail | Teaches floor |
| P25 per cell instead of median | Smoother target | Risky on sparse cells |
| Strict min per cell | Very smooth | Outlier-sensitive ($19/ct) |

**Recommendation:** Keep cluster rule; add **cell anchor** in model rather than only taking min price. For visualization, use **rolling median** of clean actuals (explainer charts) — not proof of market law.

## 14. Conclusion

**The problem** is not “find one ML algorithm with lowest MAPE.” It is to build a **pricing system** that:

1. Matches StarGem’s **current competitive list** where the sheet is dense (S26-class behavior).
2. Exposes a **continuous, monotone-in-carat** wholesale law for tools and unseen sizes ([`continuous-pricing-surface-principles.md`](continuous-pricing-surface-principles.md)).
3. Trains on a **style-aware, cluster-cleaned** dataset ([`dataset-clean-training.json`](data/dataset-clean-training.json)) that reflects base pricing, not stale premium tails.
4. Never inverts gem grade order on user-facing ladders.

**S26 is the best interpolation policy today.** **S28 is the right structural idea but v0.2 is not production-ready** — it is low on the chart because it lacks cell anchors and has flawed grade×size carat interaction for common specs.

**Something better** is most likely **anchor + fixed S28 + shrunk monotone residual**, evaluated on **held-out cells** and **pinned cases**, not on in-sample lookup MAPE alone.

Next engineering steps: implement §10 fixes, prototype §8.1, add `research/scripts/benchmark-held-out-cells.mjs`, and extend explainer with an “S28 + anchor” curve alongside S26.
